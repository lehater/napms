# Local deployment hardening review

Status: `accepted I24 local hardening review`.

Date: 2026-09-10.

## Purpose

Record the concrete hardening applied to the supported local Docker deployment and distinguish accepted improvements from unproven production claims.

## Container findings

### Backend application image

Current evidence:
- runtime image creates dedicated uid `10001` user `napms`;
- runtime executes as `USER napms`;
- only application port 8000 is exposed inside the Compose network;
- API is not published directly to the host.

I24 adds:
- Compose `init: true` for backend-derived services so signal forwarding/process reaping is explicit;
- `no-new-privileges:true` for backend-derived services.

### Web/nginx image

Current evidence:
- only Web/nginx is published to the host;
- host binding is loopback-only by default;
- internal listen port is 8080.

I24 adds:
- Compose `init: true`;
- `no-new-privileges:true`.

The upstream nginx image's internal user/master-process model is not replaced in I24. Moving to a different unprivileged image or custom global nginx layout would add a new image/runtime contract and is deferred until there is a concrete benefit beyond the existing loopback-only local boundary.

### PostgreSQL image

PostgreSQL remains on the official `postgres:16-alpine` image and is not host-published. I24 changes network authentication to password/SCRAM for fresh volumes and verifies wrong-password rejection.

I24 does not force `no-new-privileges` or a custom user/entrypoint onto PostgreSQL because the official initialization path performs privileged filesystem/bootstrap work before dropping to the database user. Changing that boundary without dedicated image-level evidence would be speculative hardening.

## Secret/configuration findings

Accepted:
- no supported plaintext UI or DB password is committed;
- supported `make dev-up` generates credentials in process memory;
- the persistent PostgreSQL role password is rotated before dependent services start;
- raw Compose requires explicit operator-provided secret overrides;
- logs/HTTP errors must not expose connection strings or credentials.

Not claimed:
- enterprise secret store;
- encrypted-at-rest local secret persistence;
- certificate/private-key lifecycle.

Those are not required by the current local target environment.

## Dependency/build findings

Backend Python dependencies are constrained by the repository's package metadata and the CI gates exercise installation/build on each merge candidate.

P2 — Web dependency reproducibility: `web/package.json` currently uses semver ranges and the repository does not contain a package-lock file. Docker therefore runs `npm install`, so an identical source revision can resolve newer compatible transitive versions later.

I24 does not hand-author a lockfile. A trustworthy npm lock must be generated by the package manager from the actual dependency graph and reviewed as its own dependency-baseline change. This remains explicit P2 debt and does not invalidate the local runtime/recovery hardening proven here.

## Workload/performance boundary

There is no accepted local user-count, request-rate, dataset-size, latency SLO or capacity target in current requirements.

Therefore I24 does **not** invent a performance envelope or SLA. The executable evidence is limited to:
- complete fresh local product journey;
- repeatable restart on preserved state;
- backup/restore round trip;
- migration replay;
- live/ready/PostgreSQL status probes;
- existing core/PostgreSQL test suites.

A measured workload envelope becomes required when a concrete target workload is accepted. Until then, performance/capacity claims remain explicitly deferred rather than inferred from CI smoke timing.

## Result

For the current local target, the accepted hardening is:
- loopback-only public ingress;
- private PostgreSQL/API network exposure;
- password/SCRAM PostgreSQL network authentication;
- ephemeral generated local credentials with repeatable role rotation;
- non-root backend runtime;
- no-new-privileges + init for application/Web containers;
- verified backup/restore and migration replay;
- fail-closed health/status diagnostics.

Enterprise HA, secret stores, public TLS automation, external identity and capacity/SLA topology remain outside the selected local deployment contract.
